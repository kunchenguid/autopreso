# Contributing

Thanks for wanting to contribute. One rule up front:

**Human-authored pull requests targeting `main` must be raised through [`no-mistakes`](https://github.com/kunchenguid/no-mistakes).**
We require this to reduce the maintainer's burden of reviewing and merging contributions.

`no-mistakes` puts a local git proxy in front of your real remote. Pushing through it runs an AI-driven review/test/lint pipeline in an isolated worktree, forwards the push upstream only after every check passes, and opens a clean PR automatically.

A GitHub Actions check (`Require no-mistakes`) runs on PRs targeting `main` and fails if the body is missing the deterministic signature that no-mistakes writes. The release and dependency bots are exempt so their automation keeps working, but regular contributor PRs without the signature will not be reviewed or merged.

## Workflow

1. Fork the repo and clone your fork.
2. Create a branch and make your changes.
3. Initialize the gate in the repo once: `no-mistakes init`.
4. Commit your changes.
5. Push through the gate instead of pushing to `origin`:

   ```sh
   git push no-mistakes
   ```

6. Run `no-mistakes` to attach to the pipeline, watch findings, and auto-fix or review as needed.
7. Once the pipeline passes, it forwards the push upstream and opens the PR for you.

See the [no-mistakes quick start](https://kunchenguid.github.io/no-mistakes/start-here/quick-start/) for the full first-run walkthrough.

## Repo conventions

- Node 24+, plain JavaScript, ESM-only. See `AGENTS.md` for agent instructions and architecture notes.
- Tests live under `test/*.test.js` and run with `node --test`.
- Run `npm run typecheck` and `npm test` before pushing. The pipeline will run them again, but a fast local pass saves rounds.
- Do not hand-edit `CHANGELOG.md` or `.release-please-manifest.json`. They are regenerated by release-please from your conventional commit messages.
- Local Moonshine sidecar binaries under `packages/*/bin/` are also generated artifacts (built by `npm run build:moonshine-sidecars` on macOS). Don't check them in by hand.

## Releases

release-please runs in monorepo manifest mode (`release-please-config.json`, `.github/workflows/release-please.yml`) with two independently versioned components:

- **`autopreso`** (root) - the CLI npm package. Bumps on any conventional commit except those that only touch the sidecar paths listed in `release-please-config.json`.
- **`moonshine-sidecars`** (`packages/moonshine-darwin-arm64`) - the `@autopreso/moonshine-darwin-{arm64,x64}` packages. Bumps only when commits touch the sidecar paths. The arm64 package is the anchor; release-please `extra-files` mirror its version into `packages/moonshine-darwin-x64/package.json` and both root `optionalDependencies` entries, so the two sidecars always share one version.

What that means in practice:

- A change to `src/`, `public/`, or `test/` only bumps autopreso, and the sidecar publish job (the Python/PyInstaller build) is skipped.
- A change to `moonshine-sidecar.config.json` (for example bumping `moonshineVoiceVersion`) bumps the sidecars. CI builds the binaries on `macos-15`, which recent `moonshine-voice` wheels require, and publishes both packages. A commit touching both kinds of paths bumps both components in one release PR.
- Sidecar binaries are built by `scripts/build-moonshine-sidecars.js`, which only runs on macOS. `scripts/prepare-release-packages.js` only verifies that each sidecar version matches the root `optionalDependencies` entry and that the binary exists; release-please owns version writing.
- The published sidecar version may lag autopreso by design, so users do not re-download the same binary on every CLI patch.
- Every `pull_request` workflow uses `paths-ignore` over the release-please output set so release PRs create zero CI runs; `test/release-ci-exclusions.test.js` guards drift. Both publish jobs regenerate `package-lock.json` with `npm install --package-lock-only` before `npm ci`, so there is no PR-time lockfile sync workflow.
